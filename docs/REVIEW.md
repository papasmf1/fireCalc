## 2. 이슈 목록

### [치명]

#### C-1. 시뮬레이터·ETF 비교·대시보드가 실제 데이터 없이 가짜 값으로 동작
- 파일: `src/app/simulate/page.tsx:11`, `src/app/etfs/page.tsx:4`
- 문제: `/simulate` 는 `src/lib/sim` 의 `runBacktest` 를 호출하지 않는다. 자산 추이는 하드코딩 `previous * 1.006 + monthly * 1.03^년` (월 0.6% 고정 수익, 적립 3% 증가 고정)이고, 몬테카를로 입력도 `0.6 + Math.sin(i) * 3` 가상 수익률이다. ETF 데이터·환율 JSON·`loadEtfs()` 는 어느 페이지에서도 사용되지 않는다. `/etfs` 의 카드별 막대도 `20 + (i*13)%75` 로 만든 장식이다.
- 재현: `/simulate` 에서 ETF 비중·기간·리밸런싱 스위치를 바꿔도 20년 값이 바뀌지 않는 것이 코드상 확인된다. 기본값(초기 5천만, 월 200만, 20년) → 최종 자산 약 **15.5억원** 은 순수 `1.006` 복리 결과이며 데이터와 무관.
- 영향: 사용자가 가짜 결과를 실제 백테스트로 오해. 제품 목적 자체가 미충족.
- 수정 제안: `loadEtfs()` + 월별 환율을 서버에서 읽어 월수익률 시계열(`adjClose` 비율, 환율 정렬)을 만들어 클라이언트 컴포넌트에 props로 전달하고, `runBacktest`/`monteCarlo`/`maxDrawdown` 에 연결. 가짜 상수 제거.

#### C-2. 과거 환율 모드에서도 초기 투자금을 `fixedFx` 로 환전
- 파일: `src/lib/sim/index.ts:12`
- 문제: `usd = initialKrw / input.fixedFx` 가 모드와 무관하게 적용된다. PLAN은 "환전 시점의 그 달 환율" 이다. 초기금을 첫 달 환율로 환전하고(historical), 평가·환전은 같은 시점 환율로 일관돼야 한다.
- 재현(검증함): 초기 1,000만원, 수익률 0%, 첫 달 환율 2,000, `fixedFx=1000`, historical → 첫 달 평가액 **20,000,000원**(원금의 2배). 기대값 10,000,000원. 환율 변화만으로 100% 수익이 생김.
- 수정 제안: 초기금도 첫 달 환율(historical) 또는 `fixedFx`(fixed)로 환전. 적립은 월초 환전/월말 수익 반영 순서를 문서화.

#### C-3. 리밸런싱이 구현되어 있지 않음 (전체를 단일 포트폴리오 수익률로 합산)
- 파일: `src/lib/sim/index.ts:17,19`
- 문제: 매월 `Σ weight × return` 으로 전체 자산에 곱하므로 사실상 **매월 리밸런싱**이다. "연 1회" 분기문은 `usd *= 1` 로 아무 일도 하지 않는다. "없음(buy & hold)" 옵션이 존재하지 않으며, 두 옵션 결과가 항상 같다. 특히 QLD(2x) 포함 시 리밸런싱 효과가 크게 왜곡된다.
- 수정 제안: 티커별 보유가치 벡터를 유지(`holdings[ticker]`)하고, 월 수익률은 각자 적용, 적립은 목표 비중으로 배분. 연 1회 시점에만 목표 비중으로 재배분.

#### C-4. `summary.json` 이 Zod 스키마와 맞지 않아 **항상 fixture(가짜) 값으로 대체됨**
- 파일: `src/lib/data/schema.ts:17-18`, `src/lib/data/loader.ts:8-10,15-17`
- 문제: 실제 `data/summary.json` 은 `{ generatedAt, notes, tickers: { VOO: { periods: { "5y": { USD:{...}, KRW:{...} } } } } }` 구조인데, `summarySchema` 는 `Record<ticker, Record<period, metric>>` 를 기대한다. 또한 `bestYear/worstYear` 는 실제로 `{year, return}` 객체인데 스키마는 number 다. 파싱이 실패하면 `readJson` 의 `catch {}` 가 **에러를 삼키고 fallback 을 반환**한다.
- 재현(검증함): zod 로 실제 파일 파싱 → `invalid_type: path ["generatedAt"] expected record`. 결과적으로 `/` 와 `/etfs` 는 모든 ETF 에 **CAGR 8.0%, 변동성 16.0%, MDD -28.0%** 를 표시한다(5개 모두 동일). Haiku의 실제 수치(예: VOO 5y CAGR 12.0%)는 화면에 나오지 않는다. 사용자 눈에는 "그럴듯한" 값이라 발견하기도 어렵다.
- 영향: 가장 위험한 형태의 버그(조용한 가짜 데이터). IMPLEMENTATION.md 의 "실제 파일이 생기면 자동으로 우선 사용" 이 사실이 아님.
- 수정 제안: (1) 스키마를 실제 구조에 맞춤(USD/KRW 분리, `coverage`, `start/end`, `bestYear: {year,return}`, 오류 객체 허용), (2) fallback 은 `NODE_ENV !== 'production'` 이나 파일 부재일 때만 쓰고 **파싱 오류는 로그/화면에 경고**, (3) fixture 사용 시 화면에 배지 표시, (4) 스키마 테스트 추가(실제 `data/*.json` 을 파싱하는 테스트).

#### C-5. 짧은 데이터 ETF(SPYQ, SCHD)에 대한 UI 안내·백테스트 처리 없음
- 파일: `src/app/etfs/page.tsx:4`, `src/app/page.tsx:8-10`, `src/lib/sim/index.ts:11,17`
- 문제:
  - SPYQ(Tradr 2X Long SPY Quarterly, 2024-09/10 상장, 26행/25개월)는 `summary.json` 에서 5y/10y/20y 가 **동일 값**(CAGR 21.67% 등)이다. 현재 UI는 fixture 때문에 이 사실이 드러나지 않지만, C-4 를 고치면 세 열에 같은 숫자가 나란히 표시되어 "SPYQ 는 20년 21.7%" 로 읽힌다. 코드에 `months`/`coverage` 사용처가 없다.
  - SCHD 20년 열은 실제 15년(179개월)인데 "20년" 이라고 표시될 것이다.
  - 2배·분기 리셋 상품이라는 성격(일간 2x QLD 와 직접 비교 불가) 경고도 없다. 25개월 CAGR 은 연환산 자체가 통계적으로 의미가 약하다.
  - `runBacktest` 는 `Object.values(input.returns)[0]` 의 날짜를 기준 축으로 삼는다. 티커별 배열을 **인덱스(month)로** 조회하므로(`returns[ticker][month]`) 길이가 짧은 ETF가 섞이면 정렬이 어긋나고, 없는 달은 `?? 0` 으로 **수익률 0%로 조용히 처리**된다.
- 재현(검증함): A(2개월), B(1개월, 둘째 달 데이터)에 각 50% → B의 데이터가 첫째 달에 적용되고, 비중 합계 100%가 아닌 경우도 그대로 계산. 비중 합 0.5 입력도 거부하지 않음.
- 수정 제안: 날짜 키 기반 inner-join으로 정렬. 선택한 포트폴리오의 **공통 구간**이 백테스트 기간보다 짧으면 (a) 기간을 공통 구간으로 줄이고 "SPYQ 데이터 25개월 한정으로 기간이 N개월로 단축" 안내, 또는 (b) 해당 ETF 제외를 선택하게 함. 비중 합 100% 검증 필수. UI에는 `months < 요청기간` 일 때 `※ 실제 N개월` 배지, SCHD "20년 → 약 15년", SPYQ "상장 약 2년 — 기간별 비교 불가, 레버리지 분기 리셋 상품" 표시. SPYQ는 5y/10y/20y 열을 `—` 로 비워도 좋다.

### [중요]

#### I-1. 양도세 처리에 오류 가능성 (연 단위 개념 부재)
- 파일: `src/lib/sim/index.ts:8`
- 문제: `afterTaxGain` 은 인자로 받은 `gainKrw` 하나에 250만원 공제를 적용한다. 공제는 **연 단위**이므로 전체 기간 누적 이익에 한 번만 적용하면 수 년간 과세를 과소 추정한다. 또 (a) 매도 시점 이익(실현손익)이 아니라 평가이익을 쓰는지 정의가 없고, (b) 손실 시 음수를 그대로 반환(검증: 이익 -500만원 → -500만원, 정상)하지만 연간 손익통산·이월은 없고, (c) 배당세는 15%를 이익에서 빼므로 `gain` 이 배당을 포함하는지 이중 차감 여부가 불명확하다. 지방소득세 10%(실효 22%)는 22% 안에 포함된 것으로 OK.
- 검증: 이익 1,000만원/배당 100만원 → 8,200,000원 (손계산 일치: 10M − 1M×15% − (10M−2.5M)×22% = 8.2M). 이익 200만원 → 2,000,000원(공제 내 무과세, 일치). **단일 연도 기준으로는 정확**.
- 수정 제안: 연도별로 실현이익 집계 후 해마다 250만원 공제를 적용하는 `taxByYear` 로 변경하고, 은퇴 후 인출 시 실현이익 계산 방식을 단순화 모델로 명시.

#### I-2. 몬테카를로가 적립기를 시뮬레이션하지 않고, 수익률 단위가 숨은 가정에 의존
- 파일: `src/lib/sim/index.ts:27`, `src/app/simulate/page.tsx:11`
- 문제:
  1. 은퇴 시점 자산 분포(10/50/90)는 PLAN 상 **적립기 부트스트랩** 결과여야 하는데, 함수는 `start` 고정값에서 출발하는 인출기만 시뮬레이션한다. 적립기 분포가 없다.
  2. 수익률을 `/100` 하므로 **퍼센트 단위 입력**을 가정한다. 반면 `BacktestPoint.return`·`MonthlyReturn.return` 은 소수(0.1=10%)다. 테스트도 `[.01,-.01]` 을 넣어 단위 혼동이 드러나지 않는다(검증: 이 입력은 ±0.01%로 해석되어 100 → 99.99999 로 사실상 변동 없음). 단위 혼동 가능성이 높은 버그 유발 지점.
  3. 인출액 `monthlySpend` 가 고정(현재가치 그대로)이라 물가상승이 반영되지 않는다. 페이지는 `living`(현재가치)을 그대로 넣으며 은퇴 시점의 미래가치로 환산하지 않는다 → 고갈 확률 과소 추정.
  4. 월 인출은 수익 반영 후 차감(월말 인출)이며, `value === 0` 으로 고갈을 판정해 중간에 0이 되었다가 복구되는 경우는 없으므로 의미는 맞다.
  5. 환율이 은퇴 후 원화 평가에 어떻게 반영되는지 불명(원화 수익률 사용 여부).
- 재현(검증함): 페이지 기본값 — 은퇴 자산 15.5억, 월 250만 → 고갈 확률 0.0%. 월 생활비 물가 2.5% 로 20년 상승 시 은퇴 시점 월 4,097,000원이 필요하나 모델은 250만원을 쓴다.
- 수정 제안: 월수익률 단위를 소수로 통일(함수 내 `/100` 제거). 적립기+인출기를 한 경로로 시뮬레이션(`runs × (accumMonths + retireMonths)`)하고 같은 인덱스 샘플링으로 원화·달러를 함께 계산. 인출액에 `(1+inflation)^(년)` 적용.

#### I-3. FIRE 목표액에 물가상승 미반영
- 파일: `src/lib/sim/index.ts:6`, `src/app/simulate/page.tsx:11`
- 문제: `fireTarget(monthly, rate) = 월×12/인출률` 은 현재가치 기준 계산으로 정확하다(250만 → 7.5억, 200만 → 6억; 테스트 통과). 그러나 은퇴 시점이 N년 후이므로 **은퇴 시점 명목 목표액** = `연생활비 × (1+물가)^N / 인출률` 이어야 하며, 비교 대상 자산(미래 명목 자산)과 단위가 맞지 않는다. 인출률·물가상승률 입력 UI도 없다(`fireTarget(living)` 만 호출, 기본 4% 고정).
- 재현(검증함): 월 250만, 20년 후 은퇴, 물가 2.5% → 명목 목표액 **약 12.29억원**, 앱 표시는 7.5억원. "달성 가능" 판정이 과대 평가됨.
- 수정 제안: `fireTarget({monthlyLivingKrw, inflation, yearsToRetire, withdrawalRate})` 로 확장하고 "현재가치 / 명목" 을 구분해 표시. 또는 자산을 실질가치로 환산해 비교.

#### I-5. 비중·데이터 정합성 검증 부재 및 `?? 0` 로 인한 침묵 오류
- 파일: `src/lib/sim/index.ts:14,17`

- 수정 제안: 입력 검증 함수가 `Result`/예외를 반환(비중합, 길이, 날짜 정렬, 환율 누락). 환율은 `Map<date, rate>`.

#### I-7. 환율 기준일 / 평가 시점 일관성 (설계 확인 필요)
- 파일: `src/lib/sim/index.ts:14-16`
- 문제: 적립은 그 달 환율로 환전(PLAN 일치)하고 같은 달 `valueKrw = usd × fx` 로 평가한다. 그러나 환율은 **월말 종가**, 적립은 월중 행위이고 수익률은 월말-월말이므로 같은 달 내에서 "월말 환율로 환전 → 그 달 수익률을 모두 얻음" 이 되어 적립금이 1개월치 수익을 먼저 받는다(미래 정보/타이밍 이점). 월초(전월 말) 가격·환율로 매수하고 월말에 평가하는 것이 일관적이다.
- 검증: 월 100만원 단일 적립, 수익률 +10%, 환율 1000 → 1개월 후 평가 110만원(적립 직후 수익 반영). 월초 매수 기준이면 맞지만, 환율은 전월 말(=월초) 값을 써야 한다.
- 수정 제안: 적립 시점 환율을 `fx[t-1]`(전월 말) 또는 `fx[t]` 중 하나로 문서화하고 수익률·환율 정렬을 같은 기준으로 통일. 단위 테스트에 기준 명시.

### 새로 발견한 문제

#### N-1. [치명] 시뮬레이터 몬테카를로가 "적립금이 섞인 값"을 수익률로 부트스트랩
- 파일: `src/app/simulate/simulator.tsx:13`, `src/lib/sim/index.ts:7`(`return` 계산)
- 문제: `BacktestPoint.return = newTotal / previous - 1` 은 **그 달 적립금 유입까지 포함한 자산 증가율**이다. 시뮬레이터가 `backtest.map(p => p.return)` 을 몬테카를로 수익률 풀로 사용하므로 시장 수익률이 아니라 적립금 증가율이 부트스트랩된다.
- 재현(검증함): 수익률 0%, 초기 1,000만원, 월 100만원 → 파생 "수익률"이 `[10.0%, 9.09%]`. VOO 만 담은 포트폴리오(초기 5천만, 월 200만)의 파생 월평균이 **2.89%**(실제 VOO 월평균 1.05%). 기본 설정(25개월) 파생 월평균 **4.22%**(연 약 64%) → 중앙값 은퇴 자산 **약 2.03조원**, 고갈 확률 **0.0%**. 화면의 몬테카를로 결과는 사실상 항상 "고갈 없음"으로 나오는 무의미한 값.
- 수정 제안: 포트폴리오 월 시장수익률(적립 전 자산 기준 `Σ w·r`, 또는 현금흐름 제거 TWR)을 별도로 반환하거나 `buildMonthlyReturns` 결과에서 가중 수익률을 직접 계산해 몬테카를로에 사용. 회귀 테스트: "수익률 0% + 적립 → 몬테카를로 입력이 전부 0".

#### N-2. [치명] SPYQ 가 비중 0%여도 전체 기간을 25개월로 고정 — 5/10/20년 선택이 무효
- 파일: `src/app/simulate/page.tsx:4`, `src/app/simulate/simulator.tsx:12`
- 문제: 서버가 **5개 ETF 전체 교집합**으로 `returns` 를 한 번만 만들어 전달한다. 클라이언트에서 비중을 바꿔도 교집합이 재계산되지 않는다. 기본 비중에 SPYQ 20%가 있으므로 화면은 "공통 가용 기간 25개월 중 25개월 사용"이 되고, 5/10/20년 탭은 모두 같은 결과를 낸다.
- 재현(검증함): 5개 전체 교집합 25개월(2024-10~), SPYQ 제외 시 **179개월**(2011-12~). 사용자가 SPYQ 를 0%로 두어도 25개월 유지.
- 영향: PLAN 의 백테스트 기간 선택과 C-5 "데이터가 짧은 ETF 포함 시 동작" 요구를 사실상 충족하지 못함. 안내문구도 "25개월을 사용합니다" 뿐이며 SPYQ 가 원인이라는 설명·해결 수단이 없음.
- 수정 제안: 서버는 티커별 월수익률 + 환율을 모두 전달하고, 클라이언트가 **비중이 0보다 큰 티커만**의 교집합으로 `buildMonthlyReturns` 를 재계산. 선택 기간이 가용 기간보다 길면 "SPYQ 때문에 N개월로 단축" 안내 + SPYQ 제외 옵션을 표시.

#### N-3. [중요] 처리되지 않는 예외 (음수 비중, 서버 컴포넌트의 변환 오류)
- 파일: `src/app/simulate/simulator.tsx:12-13`, `src/app/simulate/page.tsx:4`
- 문제: UI 의 `valid` 는 합계만 확인한다. VOO −20%, SCHD +120% 처럼 합이 100% 이고 음수가 있으면 `validateWeights` 가 `useMemo` 내부에서 throw(스크립트로 거부 동작 확인) → 클라이언트 렌더 크래시. `page.tsx` 는 `buildMonthlyReturns` 를 try/catch 없이 호출해 데이터 한 달 누락 시 페이지 전체가 500.
- 수정 제안: `valid` 에 `min ≥ 0` 포함, 입력을 0~100 으로 clamp, `useMemo` 와 서버 변환을 try/catch 하여 오류 카드 표시.

#### N-4. [중요] FIRE 목표·몬테카를로 생활비가 은퇴 시점 명목으로 환산되지 않음 (I-3/I-2 UI 미반영)
- 파일: `src/app/simulate/simulator.tsx:13`
- 문제: `fireTarget(..., 0)`(은퇴까지 연수 0) 과 `monteCarlo(..., living, ...)`(현재가치 생활비를 은퇴 후 첫해에 그대로 사용, 물가는 은퇴 *이후* 연차에만 적용)가 은퇴 전 적립 기간의 물가상승을 모두 누락한다. 기본값(월 250만원, 물가 2.5%, 20년 적립) 기준 목표액은 약 12.3억원이어야 하나 7.5억원 표시. 현재 구현에서는 적립 25개월이라 차이가 작지만 N-2 해결 후 20년이 선택되면 그대로 드러난다.
- 수정 제안: `yearsToRetire = 은퇴나이 − 현재나이`(또는 선택 기간)로 호출하고, 몬테카를로 `monthlySpend` 에 `(1+inflation)^yearsToRetire` 를 곱해 전달.

#### N-5. [중요] PLAN 시뮬레이터 요구 항목이 여전히 누락
- 파일: `src/app/simulate/simulator.tsx:11-14`
- 누락/하드코딩: 현재 나이·은퇴 나이 입력, 적립금 연 증가율(3% 하드코딩), 고정 환율(1380 하드코딩, 입력 불가), 프리셋 3종, 세금 옵션(`taxByYear` 미연결), CAGR 출력, 달러 자산 추이, 원화·달러 병기, 백테스트 결과의 원금 대비 수익률(금액만 표시), 은퇴 후 기간(240개월 고정), 고갈 확률 설명. 자산 추이는 Recharts 가 아닌 `div` 막대.

#### N-6. [개선] `/etfs`·홈의 SPYQ·기간 표시, 비교 화면 기능

### 새로 발견한 문제

#### N-8. [치명] 시뮬레이터 CAGR 이 적립금을 무시하고 `최종자산/초기금` 으로 계산
- 파일: `src/app/simulate/simulator.tsx:146-157`
- 문제: `CAGR = (최종 USD / (초기금/초기환율))^(12/개월) − 1`. 월 적립금으로 늘어난 자산이 모두 "수익"으로 잡힌다. 초기금이 0 이면 `Infinity%`.
- 재현(검증함): 수익률 0%, 초기 5천만원, 월 200만원, 60개월 → CAGR **27.7%**(정답 0%). 실제 VOO 5년 + 동일 적립 → **39.1%**(VOO 실제 약 12%). `/simulate` 기본 설정 화면이 **CAGR 33.3%** 를 표시(렌더 확인). 사용자가 가장 먼저 보는 핵심 지표이며 실제 성과를 2~3배 과장한다. 테스트·빌드가 잡지 못한다.
- 수정 제안: 현금흐름을 반영한 연환산 수익률(월 `marketReturn` 의 기하평균 `Π(1+r)^(12/n)−1`, TWR) 또는 IRR/XIRR 로 계산하고, 라벨을 "연환산 수익률(적립 제외)" 로 명시. 초기금 0 도 안전하게 처리. 회귀 테스트: "0% 수익률 + 적립 → CAGR 0%".

#### N-9. [중요] `/etfs` 연도별 수익률 표가 열 정렬·수치 모두 틀림
- 파일: `src/app/etfs/page.tsx`(annual 계산), `src/app/etfs/comparison.tsx:83-99`
- 문제: (1) 헤더는 `series[0]`(VOO, 2006~2026) 연도만 사용하고 각 행은 자기 연도 셀을 순서대로 채워, **SPYQ(2024~2026)·SCHD(2011~)가 2006, 2007… 열 아래에 표시**된다. (2) 연 수익률을 "그 해 첫 데이터 월 → 12월" 로 계산해 1월 수익률이 빠진다.
- 재현(검증함): SPYQ 셀 3개가 2006·2007·2008 열에 표시됨. VOO 2023: 표 **18.8%** vs 실제 12월→12월 **26.3%**.
- 수정 제안: 연도를 합집합 열로 만들고 없는 해는 "—", 연 수익률은 전년 12월→당해 12월(첫 해·마지막 해는 부분 연도 표시).

#### N-10. [중요] 몬테카를로 적립 기간이 은퇴 나이와 불일치
- 파일: `src/app/simulate/simulator.tsx:113-124`
- 문제: 적립기 월수에 `usableMonths`(백테스트 구간, 예: 5년 탭이면 60개월)를 쓰면서, 은퇴 후 생활비는 `yearsToRetire`(예: 20년) 만큼 물가를 올려 사용한다. FIRE 목표액·생활비는 20년 후 기준인데 자산은 5년만 적립한 값이라 서로 모순. 은퇴 나이를 바꿔도 적립 기간이 변하지 않는다.
- 수정 제안: 몬테카를로 `accumulationMonths = yearsToRetire × 12` 로 하고 월수익률 풀은 선택한 백테스트 구간에서 부트스트랩(구간보다 길어도 재표집). 백테스트(과거 구간 재현)와 미래 시뮬레이션의 기간 개념을 화면에서 구분해 표시.

#### N-11. [중요] 프리셋이 SPYQ 를 포함해 선택 즉시 기간이 25개월로 줄고, 초기 프리셋 표시가 실제 비중과 불일치
- 파일: `src/app/simulate/simulator.tsx:59-66,185-194`
- 문제: 안정형(SCHD 50%·SPYQ 15%)과 공격형(SPYQ 10%)이 SPYQ 를 포함해 **25개월**(실측)만 사용된다. "안정형" 프리셋에 2배 레버리지 상품이 들어간 것도 부적절. 초기 상태는 `preset="stable"` 로 탭이 "안정형" 으로 강조되지만 실제 비중은 25/25/25/25/0(안정형 정의와 다름).
- 수정 제안: 안정형은 SPYQ 제외(VOO/SCHD 중심, 기간 보존), 공격형도 SPYQ 제외 또는 "SPYQ 포함 시 기간 단축" 사전 안내. 초기 `weights` 를 `preset` 과 일치시키거나 "직접 설정" 탭을 추가.

### 새로 발견한 문제

#### S-14. [중요] MoneyInput 이 입력 중 쉼표를 삽입하지 않음
- 파일: `src/components/money-input.tsx:52-62,75`
- 문제: `setDraft(raw)` 로 사용자가 친 문자열을 그대로 보관하고 포맷은 blur 시에만 한다. `1000` 을 입력하는 동안 `1000` 으로 보이고 `1,000` 은 칸을 벗어난 뒤에 나타난다. 커서 복원 코드(`digitsBefore`, `setSelectionRange`)는 포맷으로 문자열이 바뀌지 않기 때문에 사실상 의미가 없다.
- 수정 제안: `onChange` 에서 정수부만 `Intl.NumberFormat` 으로 포맷한 값을 `draft` 로 저장(소수부는 보존)하고, 커서 위치를 "커서 앞 숫자 개수" 로 복원. 테스트: 입력 `1234567` → 표시 `1,234,567`, 중간 삭제 후 커서 위치 유지.

#### S-15. [중요] "실질가치" 토글이 오늘 기준 실질이 아님
- 파일: `src/app/simulate/simulator.tsx` (`displayValues`: `Math.max(0, index − yearsToRetire×12)/12` 만큼만 할인)
- 문제: 실질 환산이 **은퇴 시점 이후**에만 적용된다. 적립기 자산은 토글을 켜도 값이 그대로(명목)이고, 은퇴 시점 값은 명목과 같다. "오늘의 구매력 기준 실질"이라면 모든 시점 `value/(1+π)^(t/12)` 이어야 하고 FIRE 목표선도 같은 기준(현재가치 `월생활비×12/인출률`)으로 그려야 한다. 현재는 목표선이 은퇴 시점 명목 고정값(13.55억)이라 실질 모드에서 선과 경로의 기준이 섞인다.
- 수정 제안: 실질 모드에서 전 구간 할인 + 목표선도 할인(또는 현재가치 목표), 화면에 "오늘 가치 기준" 명시.

#### S-13. [개선] 소소한 잔여
- `src/lib/sim/index.ts:333-468` 의 중복·미완성 `runScenarioMonteCarlo`/`cholesky`(`void need` 더미, 적립 증가율 1.03 하드코딩, 인출 없음)가 그대로 남아 같은 이름 export 가 두 개(실제 사용처는 `scenario.ts`). 삭제 권장.
- `retirementHoldings` 는 은퇴 첫 달 수익률 반영 후 스냅샷이라 `retirementValue`(`values[accumulationMonths]`)와 1개월 차이. 한 경로에서 은퇴 시 자산 30.2억 vs 스냅샷 합 27.6억. 카드의 "은퇴 시 자산"과 배당 계산 기준 시점이 어긋남 — 같은 시점으로 통일 권장.
- `formatWon` 이 큰 금액에도 원 단위 꼬리를 붙임("13억 5,458만 3,426원", "월 배당 197만원 8,807원") — 1만원 단위 반올림 또는 `억/만` 만 표시 권장.
- 비관 뷰에서 입력칸(물가 2.5%)과 실제 적용값(3%)이 달라 보임 — 표시 문구 필요.
- 시나리오별 고갈 확률은 전체 경로 기준 한 값(1.4%)을 세 카드에 반복 표시(요구사항 문구와 일치하나 정보량 낮음). 비관 vs 역사 고갈 확률 실측 1.8% vs 0.1%.

### [치명]

#### T-1. 연 12% 상한이 8종목 포트폴리오에서는 **전혀 적용되지 않음** (종목이 하나일 때만 작동)
- 파일: `src/lib/sim/scenario.ts:135-141`(`input.pessimistic && tickers.length === 1 && input.annualReturnCap != null`), `src/app/simulate/simulator.tsx:314-317`(`cappedTicker` 도 `activeEtfs.length === 1` 일 때만)
- 문제: PLAN 은 "**단일 자산** 연 기대수익률 상한 12%"(각 자산의 기대수익률에 상한). 구현은 "포트폴리오가 종목 1개일 때만" 상한을 적용한다. 기본 8종목(각 1,000만원)에서는 IBIT(연 산술 33.4%), QLD(28.7%), SPYQ(25.9%), QQQM(16.6%), JEPQ(16.3%), SCHD(13.7%) 모두 상한 없이 그대로 쓰인다. 화면에도 "상한 적용 종목" 표시가 나오지 않는다(기본 화면 렌더 확인).
- 재현(검증함): 8종목 비관 뷰에서 상한 12% 와 100% 의 `means` 가 **동일**(`true`), P50 은퇴 자산 35.8억 vs 35.8억. IBIT 단독 포트폴리오에서만 `means` 가 연 11.39% 로 줄어듦. 기본 화면 P10/P50/P90 은 **11.9억 / 38.9억 / 211.1억**, 고갈 확률 1.0%, 월 배당 충당률 P50 약 140% — "비관적 낙관론자" 뷰라고 보기 어려운 결과.
- 참고(종목별 상한을 적용해 본 시험 결과, 같은 입력): P10/P50/P90 **5.3억 / 9.7억 / 21.1억**, 고갈 확률 30.5%. 상한 유무가 결과를 4배 가까이 바꾸는 핵심 가정이다.
- 수정 제안: `tickers.length === 1` 조건 제거, 종목별로 `drift_i = min(raw_i − haircut, cap)` 적용. 화면에는 상한이 적용된 모든 종목을 나열("상한 적용: IBIT, QLD, SPYQ, QQQM, JEPQ, SCHD"). 테스트: 2종목 이상 포트폴리오에서 고수익 종목의 평균이 상한으로 제한됨, 상한 미만 종목(GLD 10.1%)은 불변.

### [중요]

#### T-2. 상한이 헤어컷 **이전**에 적용되어 순서가 PLAN 과 다름
- 파일: `src/lib/sim/scenario.ts:141,186`(`means = min(rawMean, cap)` 후 `drift = means[i] − haircut/12`)
- 문제: PLAN 은 "헤어컷 적용 **후** 상한". 현재는 상한 → 헤어컷 순이라 상한이 걸리는 종목의 실제 연 기대수익률이 12%가 아니라 **약 9.4%**(= 11.39% − 2%p). 재현(IBIT·QLD 단독): 유효 drift 연 9.39%. 상한 미만 종목(GLD 10.1%)은 8.1%로 정상.
- 올바른 값: IBIT 33.4% − 2%p = 31.4% → 상한 12%, QLD 26.7% → 12%, GLD 8.1% 그대로.
- 수정 제안: `drift_i = min(mean_i − haircut/12, monthlyCap)`.
- 단위 변환 자체(연 12% → 월 `1.12^(1/12) − 1 = 0.949%`, 복리 기준 기대 연수익률)는 정확하다.

#### T-3. 상한 테스트가 단일 종목 케이스만 검증해 T-1 을 놓침
- 파일: `src/lib/sim/index.test.ts:151-`
- 문제: `weights: { IBIT: 1 }` 만 테스트. 다종목·헤어컷 후 순서·역사 뷰 미적용·표시 종목 목록 테스트가 없다.
